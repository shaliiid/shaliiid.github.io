Overview

How do you spec a course management system before writing a line of code?

PCMS (Professor Course Management System) is an open-source desktop tool that lets professors view their courses for the semester, manage a class roster, update assignment weights, and communicate with colleagues — all from one place, instead of scattered across a university's broader systems.

Before any code went into the repository, our four-person team wrote a full Software Requirements Specification following the IEEE SRS standard, defining exactly what the system would do, who it was for, and what still needed deciding.

Secure professor login

Authentication with hashed passwords and role-based access so only professors can see their own rosters.

Course & roster management

View assigned courses, search enrolled students, and manage weighted grades per assignment.

Dashboard & social tab

A real-time overview of courses and notifications, plus a space for professors to post announcements to each other.

Problem

Professors needed a tool built around them, not the registrar.

Most institutional systems are broad, administrator-first platforms — powerful, but not built around how an individual professor actually works day to day: checking a roster, updating grade weights, or catching a quick announcement from a colleague. PCMS set out to be a lighter, open-source, professor-first alternative.

But before we could build that, a four-person team had to agree on what "course management" actually meant for this project. Writing a full IEEE-format SRS forced us to separate must-haves from nice-to-haves early, and to explicitly flag the decisions we weren't ready to make yet — like which database to build on — instead of guessing and re-deciding mid-build.

Process

Writing the spec as if the system already existed.

We followed the IEEE SRS template from product scope through to individual screens — login, dashboard, course view, student view, and a social tab — then broke the system into prioritized features. Authentication and profile management came first as high priority, with dashboard activity and roster management scoped right behind it as medium priority.

We also wrote out the nonfunctional side most student projects skip: performance targets (dashboard loads within 2 seconds, roster queries under 1 second, support for 50 concurrent sessions), safety requirements like automated 24-hour backups, and security rules like BCrypt password hashing and 30-minute session timeouts — plus FERPA compliance as an explicit business rule, since real student data privacy isn't optional.

Outcome

A working JavaFX desktop app professors can use to manage courses, rosters, grades, and each other.

We built the full application against that spec: secure login, a professor dashboard, course creation, roster management with weighted grades, and a social tab so professors can post announcements and collaborate with colleagues on the platform.

The database question got resolved as we built — we landed on Firebase and a NoSQL database for authentication, data storage, and real-time updates, rather than the SQL options the SRS had left open. That turned out to be a better fit for keeping the dashboard's activity feed and notifications current in real time.

Reflection

What I learned

Requirements before pixels

Writing stimulus/response sequences and functional requirements before touching JavaFX forced our team of four to agree on edge cases — like a 30-minute session timeout, or exactly who can see a student ID number — that we'd have otherwise only discovered mid-build.

Designing for who shouldn't see what

Business rules like "only a professor can view rosters assigned to them" and FERPA compliance made permissions a first-class design decision from day one, instead of a feature bolted on after the fact.
