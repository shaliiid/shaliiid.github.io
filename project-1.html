Overview

How do you design a shelter database before you've picked your data structures?

This is a personal, ongoing project I'm building with my peer: a Python desktop app for a local animal shelter to track dogs and cats through intake, care, and adoption, alongside the volunteers who keep the shelter running.

We're also using it as a chance to actually apply what we're learning in our coursework — data structures for animal records, a SQL backend for volunteer data, a queues and search for supply warnings — instead of reaching for one generic structure for everything.

Animal records

Name, intake date, walking difficulty, medicine, age, sex, and adoption status from Application Pending through Adopted.

Volunteer scheduling

A SQL-backed volunteer list with shift assignments, walking-difficulty clearance, and shift-leader roles.

Supply warnings

A priority queue to flag low food, medicine, and bowl supplies before they run out.

Problem

One system, three very different kinds of data.

Animal records, volunteer schedules, and supply counts all need to live in the same system, but they don't behave the same way. Animal intake grows and shrinks like a list, volunteer information needs relational lookups (who's on shift with whom, who's cleared to walk which dogs), and supply counts need to actively trigger a warning before they hit zero, not just sit there as a number.

Picking the right structure for each piece — instead of forcing everything into one shape because it's simpler to build — became the real design problem before any GUI work started.

Process

Sketching the volunteer schema before writing a line of SQL.

Before touching the database, I mapped the Volunteers table on paper — name, ID, phone, email, rank, and join/leave dates — and how it connects outward to Shifts (hours, date, time, notes) and to Dogs through a walking-difficulty clearance level. I also sketched a smaller "shift buddies" idea: using a shared shift ID as a foreign key to surface which volunteers had worked together, a nice-to-have that only works if the relationships are modeled correctly from the start.

We ranked every feature by priority before building anything — animal records and adoption status came first, with a shift calendar and comments explicitly pushed to "later" — and weighed PySimpleGUI against the Qt framework for the interface layer, prototyping both in Thonny.

Progress

Still in progress — this page reflects where the design and build currently stand, not a finished product.

So far, the core data models are mapped out: animal records, the volunteer/shift schema, and the supply priority queue. Next up is wiring the SQL backend for volunteers, building out the GUI shell, then layering in the binary search tree for search and the low-supply warning system. Lower-priority features like a shift calendar and comments are intentionally saved for last. Alongside with designing a GUI for easily accessibility and understanding with the volunteers.

Reflection

What I'm learning so far

Coursework goes beyond homework

Matching each feature to the structure that actually fits it — an ArrayList for records, SQL for relational volunteer data, a priority queue for supply alerts — made coursework concepts click in a way lecture slides never did.

Design the relationships before the interface

Sketching how Volunteers, Shifts, and Dogs connect — down to a shared shift ID as a foreign key — before opening a GUI builder is already saving me from having to redo the schema later.
